# 座席クラス機能実装計画 - 概要

## 目的
Galaxium Travelsに3つの座席クラス（Economy、Business、Galaxium）を導入し、各クラスで異なる価格と座席数を管理できるようにする。

## 座席クラスの定義

### Economy（エコノミー）
- 基本クラス
- 標準価格
- 最も多くの座席数

### Business（ビジネス）
- 中級クラス
- Economy価格の約2倍
- 中程度の座席数

### Galaxium（ギャラクシウム）
- プレミアムクラス
- Economy価格の約3-4倍
- 最も少ない座席数
- 特別なアメニティとサービス

## 影響範囲

### バックエンド
1. **データベーススキーマ変更**
   - `Flight`モデルの拡張
   - `Booking`モデルの拡張
   - マイグレーション戦略

2. **API変更**
   - スキーマ定義の更新
   - サービス層のロジック変更
   - エンドポイントの拡張

3. **データシード**
   - 既存フライトデータの更新
   - 座席クラス別データの生成

### フロントエンド
1. **型定義**
   - TypeScript型の更新
   - 新しいインターフェース追加

2. **UI/UX**
   - フライトカードの座席クラス表示
   - 予約時の座席クラス選択
   - 価格表示の更新

3. **状態管理**
   - 座席クラス選択の管理
   - フィルタリング機能の拡張

## 実装の優先順位

### Phase 1: データモデルとバックエンド（必須）
- データベーススキーマの変更
- APIスキーマの更新
- サービス層のロジック実装

### Phase 2: フロントエンド基本機能（必須）
- 型定義の更新
- 座席クラス選択UI
- 予約フローの更新

### Phase 3: 拡張機能（オプション）
- 座席クラスによるフィルタリング
- 座席クラス比較機能
- アップグレード機能

## 互換性の考慮事項

### 既存データの移行
- 既存のフライトデータは全てEconomyクラスとして扱う
- 既存の予約データもEconomyクラスとして扱う
- `price`と`seats_available`フィールドは後方互換性のため保持

### APIの後方互換性
- 座席クラスを指定しない予約リクエストはEconomyとして処理
- 既存のレスポンス形式を維持しつつ、新しいフィールドを追加
